## 1. 定位（最高优先级约束）

**公司内部科研人员的技术调研工具**，不是高校文献综述工具、不是通用市场调研工具。

同时服务两个判断：
- **技术可行性**（学术线回答「能不能做」）
- **市场价值**（市场线回答「值不值得做」）

输出对象是**立项会决策者**，不是研究者本人。所有输出服务于「要不要立项 / 怎么切入 / 值不值得投入」。

## 2. 三条线的关系

学术线与市场线**不是并列拼接，是交叉**：

```
学术线（采集）→ 技术成熟度证据     → 回答「能不能做」
市场线（采集）→ 竞争格局证据       → 回答「值不值得做」
定位线（分析）→ 吃上面两条 + 我方条件 → 机会定位矩阵（该不该做、做哪条、怎么切）
```

- 单独看任何一条线都会误判
- 两条线必须以**「技术路线」为主键**组织，才能交叉
- 定位不是两条线的总结，是交叉后产生的**第三种结论**

**定位线的输入精度（回复校正）**：定位线不直接检索原始数据，但吃**带追溯字段**的结构化产出——学术产出含 DOI、市场产出含来源 URL。它要对矩阵每格「可追溯到来源」负责，所以追溯字段必须在它的输入里。

## 3. 可信度必须分级（不可妥协）

两条线数据源性质不同，**不能用同一套可溯源标准**：

| 线 | 数据源 | 可溯源标准 | 可信度等级 |
|---|---|---|---|
| 学术线 | 权威学术库 | DOI 可核 | 🟢 可核 |
| 市场线 | 网页/新闻/官网/专利库 | 来源 URL + 抓取日期 + 来源类型 | 🟢官方 / 🟡二手 / 🔴推断 |

铁律：
- 学术线：文献表由代码生成，LLM 绝不参与（沿用 v0.1 可溯源铁律）
- 市场线：做不到 DOI 级就明确承认。每条信息必须带来源 + 日期 + 可信度等级
- **绝不用学术线标准要求市场线**——否则逼 LLM 编造来源，制造信任黑洞
- 市场信息无来源，宁可不写，不许编

## 4. 必须允许「不做」和「观望」

- 定位结论必须允许是「没有值得做的」
- 定位矩阵必须有「不建议」「观望」行，不能全是「推荐」
- **一份没有排除项的定位报告，等于没做定位**

## 5. 我方条件是硬依赖 + 更新机制

定位线必须有「我方条件」输入。没有它只能输出通用建议，价值归零。

我方条件**常驻**于 `knowledge/company_profile.yaml`（不是每次重填）。分两块：

### 5.1 static 块（agent 只读不写）
公司现有能力（产线/渠道/客户/专利）、商业模式假设、约束（预算/时间/红线）、决策要回答的问题（决定两条线权重）。

### 5.2 dynamic 块（agent 可提议追加，走记忆库 pending 流程）
历史判断（上次否掉什么、为什么）。LLM 只提议、人工确认后生效，避免「我方条件错了污染所有后续定位」。

### 5.3 脱敏三件套（public 仓库红线，已确认）
- `knowledge/company_profile.example.yaml` 入库，**注释写足**（真实文件 gitignore 后，example 是唯一填表依据）
- `knowledge/company_profile.yaml` gitignore
- `scripts/check_sensitive.sh` 进 pre-commit，检查是否有非 example 文件被 track（防手滑 force add / 改名绕过）

## 6. 实施顺序（8 步，不可跳）

回复确认微调：比原文档多了第 2、3 步（定 schema）——**格式没定死就动手，容易写成「能跑但结构不对」，照样返工**。

1. **定死 `company_profile.yaml` 结构**（含 static/dynamic 分块）——定位线输入，不定死后面全白做
2. **定死学术线「标注/聚类」输出 schema**（含 `evidence_sentence` 字段）
3. **定死市场线「标注/聚类」输出 schema**（含来源、可信度、`coverage` 字段）
4. 改造学术线（代码采集 → 单次标注调用）
5. 改造市场线（同）
6. 新增定位线
7. 改输出层（一页纸决策摘要 + 机会定位矩阵）
8. 改 main.py 串起来

**基线已就位**：v0.1.1 tag 已打，v0.2 改动大可回滚。

## 7. Crew 形态（3 次 LLM 调用，回复确认）

一次改造到位，不先写三角色再砍——「角色」概念一旦进代码，即使后面砍，prompt 里的 role 定义/任务描述残留清理成本更高。

```
学术线：代码采集 → 单次「标注/聚类」LLM 调用 → [{路线, 成熟度, 关键文献, 信号, evidence_sentence}]
市场线：代码采集 → 单次「标注/聚类」LLM 调用 → [{路线, 竞品, 专利, 动态, 来源, 可信度, coverage}]
定位线：单次 LLM 调用（吃两个产出 + 我方条件）→ 机会定位矩阵
```

关键约束（回复补充）：
- 学术线「标注」是**分类 + 抽取证据二合一**，必须引摘要原句（成熟度标签附 `evidence_sentence`），不是纯分类
- 三次调用职责清晰，每次输入输出都是结构化数据

## 8. 技术路线对齐（主键难点，回复确认两点补充）

方案（已确认）：路线标签从 `domain_lexicon.py` 术语表派生，LLM 只能贴表内标签 + 一个「其他」。中英对照与同义词已在词典维护，压掉大部分对齐误差。

补充 1：**「其他」必须可审计**。单次跑完「其他」占比 >30% → 报警，说明术语表覆盖不够。「其他」变垃圾堆就失去对齐能力。

补充 2：**术语表带版本**。路线标签一旦定下，历史报告的路线名不能变。`domain_lexicon.py` 的路线表带版本号，改表时旧报告仍能按旧版本解析——为了「跑第二次能和第一次横向对比」，这是公司科研核心用法。

## 9. 专利检索降级（回复确认 + 补充）

降级方案（已确认）：v0.2 市场线 = Web 检索（Tavily/DuckDuckGo）+ 从结果抽专利信息，**不建 `patent_tool.py`**。专利列允许「信息不足」，不硬编。

补充：区分两种「信息不足」，措辞不同防误判：
- **「检索了，没有相关信息」** → 可能真没有，也可能检索词不对
- **「检索工具覆盖不到」** → 明确能力边界

市场线产出给专利字段加 `coverage: full / partial / none` 标记。

## 10. 输出层

```
reports/
├── decision_summary.md          # 一页纸决策摘要（首页，给领导看，最先成型）
├── opportunity_matrix.md        # 机会定位矩阵（核心交付物）
├── academic_report.md           # 学术证据报告
├── academic_references.tsv      # 文献表（代码生成，DOI 可核）
├── market_report.md             # 市场证据报告
├── market_sources.tsv           # 来源清单（URL + 日期 + 可信度）
└── raw/                         # 原始数据附件
```

一页纸决策摘要结构：
1. 结论先行（做 / 观望 / 不做）
2. 推荐切入方向（2~3 个）
3. 三条理由（对应学术/市场/我方）
4. 主要风险
5. 建议动作

## 11. 验收标准

**学术线**
- 文献表由代码生成，DOI 抽检 100% 可核
- 每条文献有「技术路线」「成熟度」标签，且成熟度有摘要原句依据

**市场线**
- 每条信息有来源 URL + 抓取日期 + 可信度等级
- 无来源信息被剔除，不进报告

**定位线**
- 输入缺「我方条件」时**拒绝给定位结论**，而非硬编
- 输出矩阵至少有「不建议」或「观望」行
- 每格可追溯到来源（学术→DOI，市场→URL）
- 结论可追溯到具体文献/来源，不是空泛判断

**反例（做错了的样子）**
- 「综上所述，该方向前景广阔，建议关注」→ 废话，不算定位
- 把所有缝隙列出来不做减法 → 这是清单，不是定位
- 市场信息无来源仍写进报告 → 破坏可信度

## 12. 禁区（不要做）

- 不要把两条线各写一份报告再拼一起 → 必须交叉
- 不要用学术线溯源标准要求市场线 → 逼 LLM 编来源
- 不要让定位线自己去找信息 → 它只做交叉分析
- 不要动 v0.1 可溯源铁律 → 文献表仍由代码生成
- 不要为「看起来完整」保留散文式市场报告 → 市场部分必须结构化
- 不要引入新的多角色抽象「显得高级」 → 能用代码做的就用代码
- 不要把 company_profile.yaml 真实文件提交进 public 仓库
